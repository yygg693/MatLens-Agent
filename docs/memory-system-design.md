# 记忆系统设计：从"能存"到"记得对"

本文记录 MatLens 记忆系统治理的设计依据与落地取舍。原则是不闭门造车——
每条机制的取舍都能对应到一个已经跑在生产里的成熟系统，并说明我们借了什么、
没借什么、为什么。

## 一、问题实测（2026-11，127 条真实记忆）

| 现象 | 实测数据 |
|---|---|
| 近重复累积 | 17 组 / 39 条（其中一对**一字不差**，多组相似度 58%–72%） |
| 溯源缺失 | 127 条全部 `source_type = null` |
| 分类失真 | 分类靠正文 `[用户]` 前缀推断，10 条落在"其他"无从归类 |
| 合并不可逆 | 旧交互只有 `DELETE`，点错一次没法挽回 |

典型重复（水热共沉淀选盐）：

```
[材料] 前驱体盐优先选硫酸盐（共沉淀标准体系、成本低）；水热条件下须避开硝酸盐……
[结论] 水热共沉淀选盐必须避开硝酸盐——水热条件下 NO₃⁻ 会把 Mn²⁺ 氧化成 MnOOH/MnO₂……
[结论] 水热共沉淀选盐必须避开硝酸盐——水热条件下 NO₃⁻ 会把 Mn²⁺ 氧化成 MnOOH/MnO₂……（同一句出现两次）
```

**根因**：mem0 v3 的写入是 ADD-only，只按内容哈希做精确去重；而本项目每轮对话
都会触发一次事实抽取（`sync_turn`）。同一结论只要措辞漂移一次，哈希就不同，于是
被当成新记忆累积下来。哈希拦得住一字不差，拦不住换一种说法。

## 二、业界路线与取舍

### mem0 官方（v2 → v3）

- v2：让模型判定 ADD（新事实）/ UPDATE（同主题替换、保留原 id）/ DELETE（矛盾或显式遗忘）。
- v3：改成 ADD-only，单次调用只抽新事实，靠内容哈希去重，检索侧用排序弥补。
- 参考：<https://docs.mem0.ai/migration/oss-v2-to-v3>、<https://docs.mem0.ai/open-source/features/custom-update-memory-prompt>

**借什么**：不推翻 ADD-only 流程（它更快、更省一次 LLM 判定），在写入后补一层判定。
**不借什么**：不把矛盾判定交回 LLM——每轮对话都多一次推理调用，成本与时延都不划算。

### Zep / Graphiti

每条边带 `created_at / valid_at / invalid_at / expired_at` 四个时间戳，事实变更时
**失效旧边、新建边**而不是覆盖，因此可以按"某个时间点"回溯查询。

- 参考：<https://www.getzep.com/platform/graphiti/>、<https://arxiv.org/pdf/2501.13956>

**借什么**：合并采用**软失效**而不是物理删除。这是本项目最该抄的一条——用户对
"合并不可逆"的顾虑，本质是怕判错。软失效让每次合并都能一键撤销。
**不借什么**：不引入完整的四时间戳图谱模型。本地是扁平记忆列表 + 向量库，
加一套双时态会显著抬高读写与迁移成本；用一张 `id → keep_id` 的本地台账就够
覆盖"可撤销"，且不动记忆本体。

### Letta / MemGPT

OS 式分层：core memory（常驻上下文的小块，如 human/persona）｜recall memory（历史
消息，关键词+时间检索）｜archival memory（外部向量库，靠工具主动读写）。

- 参考：<https://neoneye.github.io/agent-memory-atlas/systems/letta/>

**借什么（部分）**：本项目已有天然的 core 层——`MEMORY.md` / `USER.md` 常驻注入。
**暂不做**：把 127 条扁平记忆拆成 core / archival 两级是结构性大改，影响注入、
检索、UI 三层。当前规模（百条级）下收益不明显，等记忆量上千再做。

### A-MEM（Zettelkasten）

写入时生成结构化 note（上下文描述 + 关键词 + 标签），自动与历史记忆建链，并触发
已有记忆的上下文表示更新（memory evolution）。

- 参考：<http://raw.githubusercontent.com/agiresearch/A-mem/main/README.md>、<https://arxiv.org/pdf/2502.12110>

**借什么**：写入时补结构化字段的方向是对的（分类不该靠正文前缀猜）。
**暂不做**：LLM 建链与记忆演化需要每写一条就跑一次模型调用；且本项目已有
实体图谱（86 实体 / 99 关系）承担"记忆之间有关系"的表达。

### 遗忘曲线 / 重要性衰减

按 recency（指数衰减）+ importance + 访问频次算保留分，低于阈值才淘汰。

- 参考：<https://pypi.org/project/fademem/>

**暂不做**：127 条全部是长期有效的科研设定与偏好，衰减会误删"很久没提但仍然成立"
的约束（课题方向、禁用做法）。要做也必须在有"访问计数"埋点之后，否则没有依据。

## 三、落地的东西

### 1. 写入端语义去重（治增量）

`plugins/memory/mem0/_dedup.py` —— 零依赖、不调 LLM、不依赖 embedding 判定。

判定分数由三项组合：

```
0.45 × 二元组 Jaccard + 0.45 × 单字 Jaccard + 0.10 × 长度因子
```

- 只看二元组：语序一变分数就塌（实测同义重述只剩 0.50）。
- 只看单字：会被"用户/研究"这类高频字灌成虚高。
- 长度因子：短句字面重叠天然偏低，给一点补偿。

阈值不是拍的，是在本项目 8001 个两两组合上量出来的：

| 组别 | p05 | p50 | 最大 |
|---|---|---|---|
| 已知重复对 | 0.61 | 0.74 | 1.00 |
| 无关对 | 0.07 | 0.14 | **0.59** |

0.70 处切分可捞回 20/23 个真实重复对，7978 个无关对**零误报**。据此定：

- `DUP_THRESHOLD = 0.72`（写入端自动合并）：宁漏勿错——写入是自动的，误合并没有人工兜底。
- `SUSPECT_THRESHOLD = 0.55`（复核扫描）：宁多勿少，交给人确认。

接入两条写入路径：

- `on_memory_write`（原样存储）：写前查近邻，命中就 `update` 旧条，不再新增。
- `sync_turn`（LLM 批抽取）：抽取返回的每条"新"记忆再复核一次，命中则删新条、
  把旧条更新为信息更全的表述，保持一事一条。

查重先用向量检索粗筛（`top_k=5`），再用文本相似度细判——短句的 embedding 分数普遍
虚高，不能直接当判据。整条链路失败不阻断写入（去重是优化项，不是前置条件）。

#### 实体闸门：挡住"同模板换实体"

纯字符相似度有一个结构性缺陷：**句式模板相同、只是填了不同专名的两条**，字面重叠会
很高。实测就撞上了：

```
[材料] 碳钢/低合金钢（如Q235、A36）典型密度7.80-7.85 g/cm³，抗拉强度350-550 MPa……
[材料] 铝合金（如6061-T6、7075-T6）典型密度2.68-2.80 g/cm³，抗拉强度240-310 MPa……
```

两条讲的是**两种不同材料**，却因为模板一模一样拿到 0.58 分（越过复核阈值）。照这个
分数合并，会永久丢掉一组材料参数。

因此加了一层实体闸门：抽出"既含字母又含数字"的型号/化学式 token（`Q235`、`6061-T6`、
`NCM811`，Unicode 下标先折成 ASCII 数字，使 `Li₄Ti₅O₁₂` 与 `Li4Ti5O12` 视为同一个式子）。
当**两边都点了名、却没有任何一个共同 token** 时，分数封顶 0.50——低于复核阈值，不进重复簇。

单位词（`MPa`、`g`、`cm`、`SEM`）不含数字，不会被当成实体，所以不会制造假交集；
共用同一型号的真重复（LTO 那组）仍照常命中。

### 2. 可逆合并（治存量）

`POST /api/memory/merge` `{ids, keep, mode}`：

- `mode="supersede"`（默认）：保留 `keep`，其余记进本地台账 `~/.matlens/mem0_supersede.json`，
  列表默认不展示、检索不再召回，但正文与 id 原样保留。
- `mode="delete"`：物理删除，仅在明确要清掉时使用。

`POST /api/memory/restore` `{ids}` 撤销任意条。这是 Zep 双时间轴思路的本地简化版：
**改动只发生在视图层，记忆本体不动**，所以撤销没有任何副作用。

### 3. 后端聚合（治失真）

- `GET /api/memory/facet` —— 全库分类/来源聚合 + 重复簇计数。此前前端只能拉一页
  自己数，第 61 条之后的计数永远是错的。
- `GET /api/memory/duplicates` —— 后端算好的重复簇，前端不再自己实现一套阈值
  （只保留一份本地兜底，后端不可用时才用）。

### 4. 前端

- 概览治理区显示真实数据：疑似重复 17 组 / 39 条、无来源标记 127 条、已合并 N 条（可撤销）。
- 重复视图每组一个「合并为一条」，默认保留**表述最全**的那条（不是第一条，
  避免合完反而丢信息）。
- 详情面板：属于重复组 → 「合并其余 N 条」；处于失效态 → 显示"已合并到 xxx" + 「撤销合并」。

## 四、明确没做的，以及原因

| 未做 | 原因 |
|---|---|
| 双时态图谱（valid_at / invalid_at） | 扁平列表 + 本地台账已覆盖"可撤销"，完整实现成本远高于收益 |
| core / archival 分层 | 百条规模收益不明显；等记忆量上千再评估 |
| LLM 矛盾判定（冲突单独成表） | 每轮多一次推理调用，成本与时延不划算；当前用软失效 + 人工复核兜底 |
| 重要性衰减淘汰 | 没有访问计数埋点前，衰减会误删"长期有效但很久没提"的约束 |
| 历史 127 条回填 `source_type` | 事后回填只能靠猜，猜出来的溯源比没有更糟 |

## 五、存量治理执行记录（2026-11-09）

对已有的 127 条做了一次批量合并，全部走 `supersede`（可撤销）：

- 检出的 17 组中，**1 组（碳钢 / 铝合金）判为误判并排除**，其余 16 组按"保留表述最全
  的一条、补入其余条里未覆盖的独有句子"合并。
- 结果：**作废 22 条，有效记忆 127 → 105**，合并后复核重复组归零。
- 清理：3 组在追加时把近似同义的句子又写了一遍（只差"明确"二字之类），已改写为干净表述。
- 台账 `mem0_supersede.json` 记 22 条 `id → keep_id`，全部可一键撤销；合并明细留在
  `~/.matlens/memory_merge_log.json`（含记忆原文，**不入库**）。

顺带修掉一个会让合并看起来无效的 bug：列表接口原来只给已合并条目加 `superseded_by`
标记、却不做过滤，合并完列表条数仍是 127。现在浏览与检索都按台账过滤，`total` /
`has_more` 反映的是用户实际能看到的条数，只有显式传 `include_superseded=true` 才返回
全量（前端「已合并」视图用它）。

## 六、实体图谱：为什么是零依赖 3D

原来的实体图谱用 vis-network（2D 力导向），脚本从 unpkg CDN 动态注入，加载失败就退化成文字
列表。改造时没有换一个更大的 3D 引擎，而是自己在 canvas 2D 上算透视投影，理由有三条：

1. **量级不需要引擎。** 当前 86 实体 / 99 关系，每帧要投影的只有两百多个对象。实测单帧
   1.69 ms（60fps 的预算是 16.7 ms），引一个三维引擎反而是拿几十万字节的依赖换同样的画面。
2. **离线可用。** 旧实现在无网环境下退化成文字列表；自绘没有任何外部依赖，本地服务起不来
   时也只会显示"后端不可用"，不会因为 CDN 挂掉丢功能。
3. **神经元质感需要定制。** 节点要画成"光核 + 光晕"、连线要按深度分粗细亮度、选中时要有
   脉冲沿关系流动——这些在通用引擎里都得写自定义 shader/材质，在 canvas 里就是几次
   `drawImage` 和一条贝塞尔。

分区做法：分类 → 脑区（用户/方法/材料/性质/结论/参数/其他 七区）。七个区中心由斐波那契
球面算法生成，因此互不重叠、且**布局是决定论的**——刷新页面节点不会换个位置，方便用户记住
"哪一坨是什么"。区内节点按黄金角螺旋排布，半径带一点抖动形成"皮层厚度"。

交互：拖拽旋转（带惯性）、滚轮缩放、单击选中并高亮该实体的关系、双击进入聚焦（只亮一跳
邻居，其余压暗）、自动缓慢自转（可暂停）、重置视角。

性能四件事：

- **不可见不渲染。** 3D 只在图谱视图里跑 `requestAnimationFrame`，切回列表立刻停；图谱视图
  隐藏时容器宽高为 0，此时只缓存数据不建渲染器。
- **交互自己补帧。** 标签页不可见时浏览器会停掉 rAF，只等下一帧的话拖拽"没有反应"，
  所以拖拽/缩放/选中都同步补画一帧。
- **布局不重算。** 用实体数 + 关系数 + `updated_at` 作签名，同一版图谱切 tab 回来是瞬时的。
- **请求并行。** 记忆列表、已合并条目、重复检测三个请求互不依赖，改成 `Promise.all`
  一起发；图谱数据 8 秒内复用缓存，启动预热和切视图不再各拉一次。

### 5. 记忆自己长，前端跟着长

记忆不是在页面上"存"出来的：每轮对话结束后 `sync_turn` 在后台线程把这一轮的
user / assistant 消息交给 mem0 抽取事实（`infer=True`），写库、建索引、折叠重复，全程不
阻塞对话。用户不需要在记忆页做任何操作。

前端原本只在切页和点刷新时才重拉，于是刚聊出来的记忆要手动刷新才看得见。现在记忆页
可见时每 15 秒查一次 `/api/memory/facet` 的条数（约 30ms 的本地请求），只有总条数或
已合并数真的变了才重载：列表重载保持滚动位置，图谱重载保持当前视角，新出现的实体带
三圈扩散环、并在 7 秒内显示名字——"记忆长出来了"这件事在画面上是看得见的。用户正在
编辑、搜索、开着弹窗时不打扰；搜索态只更新计数，不把正在看的结果换掉。

实测：从外部（不经页面）写入一条记忆，页面在 0.5 秒内自己出现了新行（15 秒轮询的
随机相位，最长不超过 15 秒）；删除后同样自动回落到 105 条。

### 结构诊断：图的用途是发现问题，不是好看

调研了两个把"记忆图"当调试面板而不是装饰的参考实现：

- **Hindsight Constellation View**（vectorize-io/hindsight）——实体图、可缩放画布、
  节点亮度 = 连接度、**布局决定论**（理由和我们写的一样：每次重排就建立不了直觉，
  也没法做改动前后的对比）、**链接按关系类型上色**（semantic 蓝 / temporal 青 /
  entity 琥珀 / causal 紫），以及一个提醒：*"密集的图不等于好的记忆"*，高扇出的
  实体可能是记忆版的停用词。
- **Cognee Graph Explorer** —— shift-click 两点连线看最短路径；**"删掉这条会断掉什么"**
  的模拟；**"这条被哪些回答用过"**（把溯源做成比来源更有用的信息）；过滤镜头（不匹配
  的变暗而非删除）；底部一行随操作变化的叙述（永远告诉你现在是什么状态、怎么退出去）。

落地的是最便宜也确实能挖出问题的那一项——**结构诊断**，放在图例下方，用实测数字说话：

| 指标 | 本项目实测（86 实体 / 99 关系） |
|---|---|
| 孤立实体 | 4 个：无负极电池、304 不锈钢、燃气轮机叶片、arXiv:2609.01088 |
| 最大枢纽 | 用户 · 31 条，第二名只有 8 条 |
| 只连一条 | 37 个（43%） |

三个数字指向同一个结论：**这张图目前是"以一个用户节点为中心的星形"，还不是材料之间
互相咬合的知识网络**。孤立实体是抽出来却没连上关系的噪音；用户节点 31 条边占了全部
关系的近三分之一，视觉上会压过真实结构；43% 的实体只有一条关系，说明关系抽取还很浅。

刻意没做的一件事：**没有给关系按类型上色**。Hindsight 能上色是因为它自己生成边时就带
type 字段；我们这 99 条边的 label 是模型自由生成的中文动词（40 种不同值，处理/研究/
属于/导致……），没有类型字段。硬按关键词归类再上色，是把猜出来的分类当事实展示，
比不上色更糟。要做的话应该在抽取侧就约束关系类型，而不是在渲染侧猜。

### 共现视角：给这张星形图一个对照

结构诊断说明了一件事：抽取出的关系高度集中在用户节点上。这只说明"抽取偏了"，不说明
"材料之间真的没关系"。所以加了第二个视角——**文本共现**：不看抽取出的关系，只看哪些
实体在同一条记忆里被一起提到过。它完全由原文决定，能回答一个不同的问题：材料之间到底
是被一起讨论过，还是仅仅都被写到过。

口径：长 label 先匹配并占位，避免"固态电解质"这段文字又被更短的 label 重复命中；
只画同框 ≥2 次的边，偶发一次的大多是句子碰巧同框，画上去只会变成一团毛球。

实测（105 条记忆 / 86 实体）：

- 40 条记忆里至少提到 2 个实体，共 337 对同框，其中出现 ≥2 次的有 105 对；
- **共现视角下孤立实体 43 个**——一半实体从没跟任何别的实体出现在同一条记忆里；
- 共现视角下最大枢纽变成「钙钛矿太阳能电池」23 条（关系视角是「用户」31 条）。

两张图放在**同一套位置**上（布局决定论），切换只换边集，所以能直接对比"抽取出来的关系"
和"原文实际一起出现过什么"。这个对照本身就是诊断：如果两张图差得远，说明抽取在按自己的
语义习惯编关系，而不是在记录原文里的事实。

要诚实承认的局限：**同框不等于相关**。一条清单式的记忆（"我研究 A、B、C 三种材料"）会
制造 A/B/C 两两共现，但它们之间未必存在任何实质关联。所以共现图只用来发现"原文档里到
底在讲什么"，不能拿来当关系结论。

### 最短路径：两点之间到底怎么连上的

按住 Shift 点击两个实体，用实际连过的边跑一次 BFS，把这条链路单独点亮（其余节点压到
0.10、其余边压到 0.045），状态行给出 `路径 N 跳：A → B → C`。两点不连通时明确返回
"不连通"，不硬连一条假路径。

实测：`长期稳定性 → 钙钛矿太阳能电池 → 用户`（2 跳）；路径模式下画面亮像素从
**1197** 降到 **269**，链路确实是浮出来的。

**踩坑记一笔**：验收时一直点不中节点，一度以为是命中半径太小。真实原因是 canvas 的
`devicePixelRatio` 是 1.25（画布 380 物理像素 / 303 CSS 像素），而取样脚本按 `/2` 换算
坐标，点的位置一直偏；改成 `c.width / rect.width` 之后命中率立刻正常。凡是按物理像素取
点、再换算成 `clientX/clientY` 的地方，都必须按真实比值算，不能假设是 2。

## 七、写入侧：记忆为什么画不成网

共现视图里一半实体是孤立的。动代码之前先确认：这是"记忆本身就那么写的"，还是
"图谱实体名和原文对不上"造成的统计假象？直接读向量库（`mem0_chroma/chroma.sqlite3`
的 `embedding_metadata`，`key='data'`，127 条）做核对：

| 指标 | 实测 |
|---|---|
| 文本长度 | min 14 / p50 91 / max 1321 / 平均 120 字 |
| **单句记忆** | **89 / 127** |
| 每条命中的实体数 | 0 个 37 条、1 个 41 条、≥2 个 49 条 |
| 不同实体对 | 342 对，其中出现 ≥2 次 121 对 |
| 共现孤立 | 16 / 86（按全部配对算） |
| 加别名归一后 | 13 / 86（只救回 3 个） |

结论一：**主因是记忆被原子化，不是命名不一致。** 近三分之二的记忆只含 0–1 个实体。
mem0 的 `infer=True` 把每轮对话抽成"一条一句"的原子事实——这对检索、去重、撤销都是
优点，但它天然画不成关系网：一条只讲一个实体的事实，和谁都不共现。

结论二：**别名归一收益很小。** 把 `钛酸锂(LTO)` 拆成"钛酸锂 / LTO"、Unicode 下标折
ASCII，只救回 3 个孤立。所以不值得在这上面再搭一套别名系统。

结论三：**另有 13 个实体在 127 条记忆里完全不出现**（Materials-3课题组、氧化物固态
电解质、SEI膜、石墨负极、无负极电池、机器学习XPS分析……）。它们不是记忆写法问题，
是下面这个构建缺陷的后果。

### 图谱构建的两个真缺陷

1. **缓存永不失效。** `get_graph()` 只要有 `nodes` 就直接返回，没有任何过期判定。
   `~/.matlens/graph.json` 的时间戳停在 10/9，而记忆库已经涨到 127 条、内容更新到
   11/9。这一个月里记忆在长，图一步没动。
2. **构图只取"最相关的一批"。** `_fetch_memories()` 用一次
   `mem0_search(top_k=60)`——语义检索只返回近邻，不是全量。图谱因此永远看不见库里的
   另一半，这正解释了为什么图里有实体在全部记忆中都找不到。

### 修了什么

- **全量枚举**：优先用 `list_memories` 翻页把整库拉齐，后端不支持枚举才回落到检索。
- **分批抽取 + 合并**：127 条一次塞给模型会超上下文，改成每批 45 条；新增
  `_merge_graph_parts()` 解决"每批各编一套 id"的问题——节点按 label 归一去重，各批
  原始 id 先映射到规范 id 再落地边，否则会出现第一批的节点连到第二批的节点。自环、
  悬空边、重复边一并丢掉。
- **缓存自查**：`memory_count` 与库里实际总量对不上就后台重建（5 分钟探测节流），
  GET 先返回旧图并标 `rebuilding`，不阻塞请求。
- **降级保护**：这条是被现场事故逼出来的。LLM 抽取失败时会降级成"记忆即节点"的
  启发式图——形状上就是一堆以记忆文本为 label 的散点。如果自动重建把这种产物写进
  缓存，等于用垃圾覆盖好图。`_should_replace()` 因此规定：降级产物只能替换本来就是
  降级图的缓存（或旧图为空时）。

### 现场发现的上游故障

`_get_deepseek_key()` 能取到 35 字符的 key，但实际调用返回
`401 Authentication Fails`。离线跑 3 批全量抽取，3 批全部降级成启发式——恰好把上面的
降级保护逼了出来。换上新 key 之后重建终于跑通，随即暴露出两个"分批"带来的新问题。

### 分批的两个代价，以及怎么补

**一、图被切成几块。** 模型每批只看得到自己那 45 条，批与批之间的实体它连不起来。
127 条分 3 批，第一次重建得到 7 个互不相通的连通分量（82 / 33 / 5 / 3 / 3 / 3 / 3）——
一张图七个岛。

补法：用最朴素的证据拉桥——两个实体出现在同一条记忆里。但**只补"能把两块断开的连上"
的那些**（按同框次数优先，并查集判连通），不是把所有同框对都画出来。这一条是量出来的：
不做限制时补出 372 条边，因为短名实体（`用户`、`GDC`）几乎每条记忆都出现，全补就是噪声；
限制之后只剩 1 条，而连通分量已经降到 4。桥边单独标 `kind="cooc"`，前端画成琥珀色虚线，
和模型给出的关系区分开——它表达的是"原文里一起出现过"，不是"模型认为有关系"。

**二、同一个实体被抽成好几个节点。** 第一版重建出来 `用户` 34 条边、`郭家豪` 17 条、
`用户（华中科技大学材料学院研二学生）` 10 条——同一个人三个节点；还有
`Ce₀.₇₈Gd₀.₂₀Ca₀.₀₂O₂₋δ`、`GDC-Ca共掺杂`、`GDC论文大修` 这种同一物质的不同写法。

补法放在抽取侧，不做事后归并：
- 命名规则写进 prompt：一个实体一个规范名、取最短通行写法（≤16 字）、不要把别名和
  分子式堆成一个长名、关于用户的实体一律用「用户」（不写姓名/学校/年级）。
- **跨批传已知实体**：后一批的 prompt 里带上前面各批已抽到的实体名，要求含义相同就复用
  完全相同的名称。这条是效果最大的一步——它让"用户"只剩一个节点，也让大部分语义边天然
  跨批连通，所以最终只需要 1 条桥。

### 重建前后实测

| | 旧图（10/9） | 修复后 |
|---|---|---|
| 覆盖记忆 | **50 条** | 127 条 |
| 节点 / 边 | 86 / 99 | 151 / 165（语义 164 + 桥 1） |
| 孤立实体 | 4 | 1 |
| 最大枢纽 | 用户 31 条 | 用户 29 条，第二「GDC-Ca共掺杂」21 条 |
| 连通分量 | — | 4：142 / 5 / 3 / 1 |
| 边长 label | 40 种 | 61 种 |

节点从 86 涨到 151 不是"抽得更多"，是终于看见了库里另外 77 条记忆。用户节点仍居首，但
第二名从 8 条涨到 21 条——这张图正在从"以用户为中心的星形"变成材料之间互相咬合的网络，
不过还没到。剩余 3 个碎片（5 / 3 / 1 个实体）是语义上确实没连上的孤立点，不是缺陷。

## 九、实体归一：同一物质的多种写法

### 9.1 先问一句：到底有多少组真的是同一个东西

开工前把 151 个节点的名字全部列出来对着看，再用两条互相独立的路找候选——正则规则
（括号别名 / 名称包含）和 DeepSeek 逐条判定——两边指向同一个结论：

**真正同物异名的只有 1 组，其余几乎都是上下位或同族不同牌号。**

模型给出的待判定对里，它自己否掉了绝大部分，理由写得很清楚：

| 被否掉的一对 | 理由 |
|---|---|
| `304不锈钢` / `316不锈钢` / `430不锈钢` | 差一个牌号就是两种材料 |
| `高温合金` / `镍基高温合金` | 上位与下位 |
| `钛合金` / `Ti-6Al-4V` | 合金类与其牌号 |
| `氧化物固态电解质` / `LLZO`、`LATP` | 上下位 |
| `XPS` / `ML-XPS` | 基础表征与机器学习辅助的组合手段 |
| `NCM811` / `Ni₀.₈Co₀.₁Mn₀.₁(OH)₂` | 正极材料与其共沉淀前驱体，研究对象不同 |
| `界面阻抗` / `界面阻抗降低≥50%` | 性质与参数目标，跨类别 |
| `Gd掺杂CeO₂` / `GDC-Ca共掺杂` | 差一个 Ca 掺杂元素 |

站得住的只有一组：`GDC20-Ca2` / `Ce₀.₇₈Gd₀.₂₀Ca₀.₀₂O₂₋δ` / `GDC-Ca共掺杂`——
20% Gd + 2% Ca 的掺杂量正好对应 Ce0.78Gd0.20Ca0.02O2-δ，是同一材料的中文名、化学式
和组分缩写三种写法。

这也解释了上一轮"别名归一只能救回 3 个孤立实体"的实测：不是归一没用，是这张图里
本来就没有那么多重复写法。**把"图不够密"归因于命名不一致，是一个错误假设。**

### 9.2 为什么不做自动合并

材料领域里"同族"与"同一个"只差一个下标。`304` 与 `316` 差一个牌号就是两种材料，
`Gd掺杂CeO₂` 与 `GDC-Ca共掺杂` 差一个掺杂元素就是两种材料，`Ce0.78` 与 `Ce0.8`
差 0.02 可能就是一个独立样品的配方。自动合并 = 替用户下材料学断言，而且错了之后
很难发现（图上只是少了一个节点）。

所以归一被拆成三层，越往下越保守：

1. **比对层（自动，零风险）**：`_normalize_label()` 把下标上标折成普通字符、全半角
   统一、数学减号统一成 `-`、去掉空白。只用于判断"是不是同一个写法"，**展示仍用原
   label**——`Ce₀.₇₈Gd₀.₂₀Ca₀.₀₂O₂₋δ` 里的下标是专业写法，不该为了比对被抹平。
   这一步让跨批出现的 `Ce₀.₇₈...` 与 `Ce0.78...` 自动合成一个节点，并把多出来的写法
   记进该节点的 `aliases`。
2. **提示层（自动，只列不合并）**：`_merge_candidates()` 给出"名字可能指同一实体"的
   配对，四条守卫防止乱报——必须同类别（`界面阻抗` 与 `界面阻抗降低≥50%` 跨类别）、
   短的一方不能是上位类别词（`高温合金`）、两边不能只差数字（同族牌号）、长名不能是
   `ML-` / `原位` / `机器学习` 这类组合前缀（`ML-XPS` 与 `XPS`）。
3. **归并层（人工复核后才生效）**：`~/.matlens/entity_merge.json` 里的 `groups` 才真
   合并，每组必须写 `why`（命名或化学依据）。这个文件只在本机、**不进仓库**（实体名
   来自个人记忆内容），删掉它就回到"每种写法各占一个节点"，所以归并天然可撤销。
   同一份文件的 `rejected` 字段记着明确判定为不同实体的对，用来防止将来重建时被误合。

### 9.3 一个更要紧的发现：实体名本身是不稳定的

做归并时撞上一件比"同物异名"严重得多的事：**同一批 127 条记忆，连续重建几次，
实体名和节点数一路漂。**

| 重建 | 节点 / 边 | 现象 |
|---|---|---|
| 第 1 次 | 151 / 165 | `GDC-Ca共掺杂`、`GDC论文大修` |
| 第 2 次 | 158 / 175 | 变成 `GDC-Ca`、`GDC`，归并配置按名字匹配全部失效 |
| 第 3 次 | 161 / 255 | 又出现 `GDC论文草稿`，桥接边暴涨 |
| 试"逐字摘录原文" | **242 / 264** | 名字更贴原文，但原文写法本身就多，节点直接炸开 |

原因有两个：抽取调用 `chat.completions.create()` **没设 `temperature`**，默认是采样
的；而且每次重建的 `known`（跨批复用实体名的提示）都从空开始，模型每批都自由命名。

修法三条：

- 抽取加 `temperature=0`，让同样的输入给出同样的输出；
- `known` 的初始值改成**上一版图里的全部实体名**，重建时复用既有命名而不是另起一套；
- prompt 命名规则加一条硬约束："只要与已有实体里的某个名称指同一对象，就原样使用
  那个名称，不要再缩短或改写"。同时**退回"取最短通行写法"，没有采用"逐字摘录"**——
  逐字摘录虽然稳定，但会把同一实体的不同原文写法全变成节点（实测 242 个），
  节点碎到枢纽不再有意义。

这件事的意义超出归一本身：**只要实体名不稳定，任何按名字写的配置、任何前后对比的
结构指标都不可信。** 所以在做归并之前先把命名钉住，是必要的前置。

### 9.4 结果

| | 归一前（151/165） | 归一后（165/204） |
|---|---|---|
| 孤立实体 | 1 | **0** |
| 最大枢纽 | 用户 29 条 | **GDC-Ca共掺杂 40 条** |
| 第二大 | GDC-Ca共掺杂 21 | 用户 24 |
| 叶子节点 | 94 / 151（62%） | 81 / 165（49%） |
| 已归并写法 | — | 1 个（GDC20-Ca2 → GDC-Ca共掺杂） |

枢纽从「用户」换成了材料实体——用户节点不再支配整张图，这正是从"以我为中心的星形"
转向"材料之间互相咬合"的那一步。叶子占比从 62% 降到 49%，说明多出来的节点没有全部
挂在同一条边上。

前端把这三件事都摆出来了：结构诊断里多一行「已归并 N 个写法（旧写法 → 规范名）」，
下面一行「另有 N 对名字可能指同一实体（…），没有自动合并」，详情面板里显示该节点
吸收了哪些写法以及合并依据。用户随时能核对系统到底合了什么、没合什么。

### 9.5 没做的

- **图上点击合并**：候选目前只提示，不能在界面上点一下就合。需要新增一个写
  `entity_merge.json` 的接口 + 前端确认交互，判断权仍然留在用户手里。
- **实体词典**：现在靠"上一版图的名字"做锚，属于软约束。真正的稳定方案是首次确认后
  固化一份词典（规范名 → 原文写法），抽取时强制只能用词典内的名字。它比"每次重建
  复用上次名字"更硬，但要先有人工确认的那一遍。
- **`rejected` 只做记录，还没有作为守卫参与判断**：将来若模型又把 `304`/`316` 抽成一个
  节点，现在没有机制去拆开它。

## 十、实体词典与图上合并

### 10.1 为什么"复用上一版的名字"不够

9.3 把名字漂移压住了，但那是**软锚定**：每次重建都从上一次的图里取名字。问题是
上一版图本身可能就是漂过一次的版本，锚在漂过的名字上，漂移只会被记住而不会被纠正
——它不收敛，只是漂得慢一点。

真正的解法是把名字存在图之外：一个独立的、跨重建持久存在的实体词典。

### 10.2 词典怎么工作

`~/.matlens/entity_dict.json`，格式是 `{规范名: {category, aliases, seen}}`。

- **构建时**：`known`（传给模型的"请复用这些名字"清单）优先来自词典，按 `seen`
  次数排序；词典为空才回落到上一版图。第一次重建就是"自由命名 + 顺手建词典"。
- **落地时**：`_apply_entity_dict()` 把每个节点名对齐到词典——归一后相等、或命中了
  词典里某条的 `aliases`，就改成那个规范名；这次见到的新名字登记进词典（`seen` +1），
  下次重建它也会变成要复用的名字。
- 词典和归并配置都在本机、都不进仓库——实体名来自个人记忆内容。

实测连续两次重建（127 条记忆，第二次的 `known` 全部来自词典）：

| | 没有词典 | 有词典 |
|---|---|---|
| 实体名重合率 | 89%（204→178 那次，`GDC20-Ca2` 直接消失） | **100%：165 / 165，一个不差** |
| 边数波动 | 204 → 178（13%） | 200 → 194（3%） |
| 自动归并 | 时有时无（取决于某写法恰好被抽出） | 稳定触发：`Ce0.78Gd0.20Ca0.02O2-δ` → `GDC-Ca共掺杂` |

节点集合重合率 100% 是这次改动最硬的证据：同一批记忆连续重建，实体名和节点数
完全一致，不再是"看起来差不多"。

### 10.3 图上点一下就能合

候选只提示、判断权给用户，代价是"想去合并时还得去改配置文件"。`POST /api/graph/merge`
把这个动作做成一次点击：

- 写进 `~/.matlens/entity_merge.json`（`_save_entity_merge` 保留 `rejected` 等人工
  判断记录，不会被覆盖掉）；
- 立即应用到当前缓存图，不用等下一次重建；
- 返回这次合并了哪些写法、剩余节点与边数；
- **可撤销**：删掉配置里对应条目、重建一次就恢复。

前端在详情面板里，把与当前节点相关的候选列成一行「合并到此」，并写明"合并会写进
本机配置，删掉对应条目就能撤销"。

### 10.4 一个反证：候选规则还会误报

当前 165 个节点上，系统给出的三条候选——`β型钛合金` / `α+β型钛合金`、
`GDC` / `GDC-Ca共掺杂`、`GDC` / `GDC20-Co`——**没有一条应该合**。前者是两种不同的
钛合金类型，中间那个 `GDC` 是上位的 Gd 掺杂 CeO₂，最后一个差的是掺杂元素 Co。

这同时说明两件事：候选规则（括号别名 + 名称包含）在缩写场景下会误报；如果当初做了
自动合并，这 3 条会变成 3 个错误的节点并合，而且事后很难发现。把判断权留在人手里，
代价只是多点一下。

### 10.5 还没解决的

- **边数仍会小幅波动**（200 → 194）。节点定住了，但"同一对实体之间到底有哪些关系"
  每次略有不同。这是关系抽取端的稳定性问题，需要对关系本身也加约束（例如限制关系
  动词表），是下一步。
- **叶子节点 89 / 165（54%）**：大量实体只连一条边。这不是命名问题——第七节已经量过，
  近 2/3 的记忆只含 0–1 个实体，是记忆被原子化导致的。词典解决不了它。


## 十一、关系侧：边为什么不稳

### 11.1 先量，别猜

实体名的问题（第九、十节）解决后，节点已经连续两次重建 100% 重合。但边还在动。
量出来的事实：

| 指标 | 数值 |
|---|---|
| 边 | 194 条 |
| 用到的动词 | **92 种** |
| 出现 ≥2 次的动词 | 29 种（覆盖 131 条边） |
| **只出现 1 次的动词** | **63 种** |

三分之一的关系只被用过一次。同义重叠在明处：`包含 13 / 包括 11 / 具有 16`、
`用于 8 / 采用 3 / 使用 2 / 应用于 1`、`导致 8 / 产生 1`、`研究 7 / 关注 3 / 研究方向 2`。

这和实体名是**同一类问题**——同一个语义每次换个说法。所以做法也一样：
把上次用过的词反过来喂给模型，再加上一张只收"完全同义"的小表兜底。

### 11.2 两条措施

**一、关系动词词典**（`~/.matlens/relation_dict.json`）

机制与实体词典同构：抽取时把已有动词按频次塞进 prompt（`known_rel`，取前 40 个），
抽取完把这次见到的动词登记回去。词典为空时才回落到上一版图的边标签。
批次之间也累积，让后一批接着用前一批的词。

**二、小同义表**（只 9 组、只合完全等价的）

```
包含 ← 包括 / 含有 / 涵盖        用于 ← 应用于 / 采用 / 使用 / 借助 / 利用
导致 ← 引起 / 造成 / 引发 / 致使    制备 ← 合成 / 制造 / 生成
改善 ← 提升 / 增强 / 提高 / 优化    降低 ← 减少 / 削弱
属于 ← 归类为 / 归为              研究 ← 探究 / 考察
影响 ← 作用 / 决定
```

**刻意没合的**：`测试` / `表征`（一个测性能一个看结构）、`具有` / `包含`
（材料语境里一个是性质归属、一个是成分构成）。硬合等于把真实区分抹掉——
和第九节拒绝"按关键词给关系分类上色"是同一条理由：不知道就别装作知道。

### 11.3 实测收敛

| | 改之前 | 第一次重建 | 第二次重建 |
|---|---|---|---|
| 节点 | 165 | 168 | 168 |
| 边 | 194 | 184 | 194 |
| 动词种数 | **92** | 27 | **25** |
| 只出现一次 | **63** | 5 | **7** |

两次重建的动词集合重合率 **92.6%**（run1 的 27 种里 25 种在 run2 里出现）。
边数回到 194，说明收敛不是靠丢边换来的。

图例里现在有一行诊断：`关系动词 25 种 · 7 种只出现一次（28%）`——
这个数字改一次就能看到有没有变差。

### 11.4 顺带挖出一个更脏的洞：降级图污染词典

第一次跑完收敛验证时，动词统计里冒出 `用户 / 结论 / 材料 / 其他 / 实验` ——
这些是**实体类别词**，被当成了关系。

追下去发现不是模型抽错了，而是**部分批次抽取失败时，启发式降级图被混进了语义图**。
`_heuristic_graph` 的做法是"记忆原文截 40 字当节点、同类别节点连链"，所以它产出的
节点是整句、边标签是类别名。

后果比"图难看"严重得多：这些整句节点随后被 `_apply_entity_dict` **登记进了实体词典**，
下一轮重建时又被当成「已有实体」原样喂回模型。模型于是照着长句继续起名。

实测污染规模：词典 211 条里 **46 条是记忆整句**，全部 40 字截断。其中一条写的是
真实姓名（`用户郭家豪正在撰写…`），说明"关于用户的实体一律用『用户』"这条规则
被降级路径整个绕过了。

**三处修复**：

1. **部分批次降级不进图**：抽不出来的批次直接跳过，宁可少几批的实体，也不放假节点。
   只有**全部**批次都失败时才退回启发式（否则页面空着）。
   `fallback` 只在全降级时为 True，所以部分降级光看它发现不了——
   新增 `degraded_batches` 字段单独报出来。
2. **整句不登记进词典**：`_looks_like_entity_name` 把关。
3. **清理已污染的条目**：词典 211 → 168 条，关系词典剔掉 5 个类别词。

第 2 点的判据第一版写成了"超过 16 字就是句子"，**误伤了真实实体**：
`Ce0.78Gd0.20Ca0.02O2-δ`、`Ni₀.₈Co₀.₁Mn₀.₁(OH)₂`、`Advanced Energy Materials`、
`Journal of Materials Chemistry A` 全被删了。修正后的判据：

- 带省略号 / 带 `[类别]` 前缀 → 句子（降级图的指纹）
- 剥掉括号里的化学式后不含中文 → 纯英文/化学式，放宽到 40 字（期刊名本来就长）
- 含中文 → 实体名超过 16 字基本就是句子

重跑后删 43 条、剩 168，四个被误伤的真实实体全部保住。这条判据有单测锁着
（`test_entity_name_heuristic_keeps_formulas_and_journal_names`）。

### 11.5 还没解决的

- **泛关系占比高**：`涉及 39 / 包含 29 / 具有 11`，三类"整体-部分/关联"占了 194 条边的
  41%。它们语义确实不同（不合并），但都是信息量低的通用词。要压下去得在 prompt 里
  要求"尽量用具体动词"，而这可能诱导模型乱造词——没动，先留观察。
- **叶⼦ 95 / 168（57%）** 与第十节的结论一致，仍是记忆原子化导致的，关系侧改不动它。
