# 记忆系统设计：从"能存"到"记得对"

本文记录 MatLens 记忆系统治理的设计依据与落地取舍。原则是不闭门造车——
每条机制的取舍都能对应到一个已经跑在生产里的成熟系统，并说明我们借了什么、
没借什么、为什么。

## 一、问题实测（2026-11，127 条真实记忆）

| 现象 | 实测数据 |
|---|---|
| 近重复累积 | 17 组 / 39 条（其中一对**一字不差**，多组相似度 58%–72%） |
| 溯源缺失 | 127 条全部 `source_type = null` |
| 分类失真 | 分类靠正文 `[用户]` 前缀推断，10 条落在"其他"无从归类 |
| 合并不可逆 | 旧交互只有 `DELETE`，点错一次没法挽回 |

典型重复（水热共沉淀选盐）：

```
[材料] 前驱体盐优先选硫酸盐（共沉淀标准体系、成本低）；水热条件下须避开硝酸盐……
[结论] 水热共沉淀选盐必须避开硝酸盐——水热条件下 NO₃⁻ 会把 Mn²⁺ 氧化成 MnOOH/MnO₂……
[结论] 水热共沉淀选盐必须避开硝酸盐——水热条件下 NO₃⁻ 会把 Mn²⁺ 氧化成 MnOOH/MnO₂……（同一句出现两次）
```

**根因**：mem0 v3 的写入是 ADD-only，只按内容哈希做精确去重；而本项目每轮对话
都会触发一次事实抽取（`sync_turn`）。同一结论只要措辞漂移一次，哈希就不同，于是
被当成新记忆累积下来。哈希拦得住一字不差，拦不住换一种说法。

## 二、业界路线与取舍

### mem0 官方（v2 → v3）

- v2：让模型判定 ADD（新事实）/ UPDATE（同主题替换、保留原 id）/ DELETE（矛盾或显式遗忘）。
- v3：改成 ADD-only，单次调用只抽新事实，靠内容哈希去重，检索侧用排序弥补。
- 参考：<https://docs.mem0.ai/migration/oss-v2-to-v3>、<https://docs.mem0.ai/open-source/features/custom-update-memory-prompt>

**借什么**：不推翻 ADD-only 流程（它更快、更省一次 LLM 判定），在写入后补一层判定。
**不借什么**：不把矛盾判定交回 LLM——每轮对话都多一次推理调用，成本与时延都不划算。

### Zep / Graphiti

每条边带 `created_at / valid_at / invalid_at / expired_at` 四个时间戳，事实变更时
**失效旧边、新建边**而不是覆盖，因此可以按"某个时间点"回溯查询。

- 参考：<https://www.getzep.com/platform/graphiti/>、<https://arxiv.org/pdf/2501.13956>

**借什么**：合并采用**软失效**而不是物理删除。这是本项目最该抄的一条——用户对
"合并不可逆"的顾虑，本质是怕判错。软失效让每次合并都能一键撤销。
**不借什么**：不引入完整的四时间戳图谱模型。本地是扁平记忆列表 + 向量库，
加一套双时态会显著抬高读写与迁移成本；用一张 `id → keep_id` 的本地台账就够
覆盖"可撤销"，且不动记忆本体。

### Letta / MemGPT

OS 式分层：core memory（常驻上下文的小块，如 human/persona）｜recall memory（历史
消息，关键词+时间检索）｜archival memory（外部向量库，靠工具主动读写）。

- 参考：<https://neoneye.github.io/agent-memory-atlas/systems/letta/>

**借什么（部分）**：本项目已有天然的 core 层——`MEMORY.md` / `USER.md` 常驻注入。
**暂不做**：把 127 条扁平记忆拆成 core / archival 两级是结构性大改，影响注入、
检索、UI 三层。当前规模（百条级）下收益不明显，等记忆量上千再做。

### A-MEM（Zettelkasten）

写入时生成结构化 note（上下文描述 + 关键词 + 标签），自动与历史记忆建链，并触发
已有记忆的上下文表示更新（memory evolution）。

- 参考：<http://raw.githubusercontent.com/agiresearch/A-mem/main/README.md>、<https://arxiv.org/pdf/2502.12110>

**借什么**：写入时补结构化字段的方向是对的（分类不该靠正文前缀猜）。
**暂不做**：LLM 建链与记忆演化需要每写一条就跑一次模型调用；且本项目已有
实体图谱（86 实体 / 99 关系）承担"记忆之间有关系"的表达。

### 遗忘曲线 / 重要性衰减

按 recency（指数衰减）+ importance + 访问频次算保留分，低于阈值才淘汰。

- 参考：<https://pypi.org/project/fademem/>

**暂不做**：127 条全部是长期有效的科研设定与偏好，衰减会误删"很久没提但仍然成立"
的约束（课题方向、禁用做法）。要做也必须在有"访问计数"埋点之后，否则没有依据。

## 三、落地的东西

### 1. 写入端语义去重（治增量）

`plugins/memory/mem0/_dedup.py` —— 零依赖、不调 LLM、不依赖 embedding 判定。

判定分数由三项组合：

```
0.45 × 二元组 Jaccard + 0.45 × 单字 Jaccard + 0.10 × 长度因子
```

- 只看二元组：语序一变分数就塌（实测同义重述只剩 0.50）。
- 只看单字：会被"用户/研究"这类高频字灌成虚高。
- 长度因子：短句字面重叠天然偏低，给一点补偿。

阈值不是拍的，是在本项目 8001 个两两组合上量出来的：

| 组别 | p05 | p50 | 最大 |
|---|---|---|---|
| 已知重复对 | 0.61 | 0.74 | 1.00 |
| 无关对 | 0.07 | 0.14 | **0.59** |

0.70 处切分可捞回 20/23 个真实重复对，7978 个无关对**零误报**。据此定：

- `DUP_THRESHOLD = 0.72`（写入端自动合并）：宁漏勿错——写入是自动的，误合并没有人工兜底。
- `SUSPECT_THRESHOLD = 0.55`（复核扫描）：宁多勿少，交给人确认。

接入两条写入路径：

- `on_memory_write`（原样存储）：写前查近邻，命中就 `update` 旧条，不再新增。
- `sync_turn`（LLM 批抽取）：抽取返回的每条"新"记忆再复核一次，命中则删新条、
  把旧条更新为信息更全的表述，保持一事一条。

查重先用向量检索粗筛（`top_k=5`），再用文本相似度细判——短句的 embedding 分数普遍
虚高，不能直接当判据。整条链路失败不阻断写入（去重是优化项，不是前置条件）。

#### 实体闸门：挡住"同模板换实体"

纯字符相似度有一个结构性缺陷：**句式模板相同、只是填了不同专名的两条**，字面重叠会
很高。实测就撞上了：

```
[材料] 碳钢/低合金钢（如Q235、A36）典型密度7.80-7.85 g/cm³，抗拉强度350-550 MPa……
[材料] 铝合金（如6061-T6、7075-T6）典型密度2.68-2.80 g/cm³，抗拉强度240-310 MPa……
```

两条讲的是**两种不同材料**，却因为模板一模一样拿到 0.58 分（越过复核阈值）。照这个
分数合并，会永久丢掉一组材料参数。

因此加了一层实体闸门：抽出"既含字母又含数字"的型号/化学式 token（`Q235`、`6061-T6`、
`NCM811`，Unicode 下标先折成 ASCII 数字，使 `Li₄Ti₅O₁₂` 与 `Li4Ti5O12` 视为同一个式子）。
当**两边都点了名、却没有任何一个共同 token** 时，分数封顶 0.50——低于复核阈值，不进重复簇。

单位词（`MPa`、`g`、`cm`、`SEM`）不含数字，不会被当成实体，所以不会制造假交集；
共用同一型号的真重复（LTO 那组）仍照常命中。

### 2. 可逆合并（治存量）

`POST /api/memory/merge` `{ids, keep, mode}`：

- `mode="supersede"`（默认）：保留 `keep`，其余记进本地台账 `~/.matlens/mem0_supersede.json`，
  列表默认不展示、检索不再召回，但正文与 id 原样保留。
- `mode="delete"`：物理删除，仅在明确要清掉时使用。

`POST /api/memory/restore` `{ids}` 撤销任意条。这是 Zep 双时间轴思路的本地简化版：
**改动只发生在视图层，记忆本体不动**，所以撤销没有任何副作用。

### 3. 后端聚合（治失真）

- `GET /api/memory/facet` —— 全库分类/来源聚合 + 重复簇计数。此前前端只能拉一页
  自己数，第 61 条之后的计数永远是错的。
- `GET /api/memory/duplicates` —— 后端算好的重复簇，前端不再自己实现一套阈值
  （只保留一份本地兜底，后端不可用时才用）。

### 4. 前端

- 概览治理区显示真实数据：疑似重复 17 组 / 39 条、无来源标记 127 条、已合并 N 条（可撤销）。
- 重复视图每组一个「合并为一条」，默认保留**表述最全**的那条（不是第一条，
  避免合完反而丢信息）。
- 详情面板：属于重复组 → 「合并其余 N 条」；处于失效态 → 显示"已合并到 xxx" + 「撤销合并」。

## 四、明确没做的，以及原因

| 未做 | 原因 |
|---|---|
| 双时态图谱（valid_at / invalid_at） | 扁平列表 + 本地台账已覆盖"可撤销"，完整实现成本远高于收益 |
| core / archival 分层 | 百条规模收益不明显；等记忆量上千再评估 |
| LLM 矛盾判定（冲突单独成表） | 每轮多一次推理调用，成本与时延不划算；当前用软失效 + 人工复核兜底 |
| 重要性衰减淘汰 | 没有访问计数埋点前，衰减会误删"长期有效但很久没提"的约束 |
| 历史 127 条回填 `source_type` | 事后回填只能靠猜，猜出来的溯源比没有更糟 |

## 五、存量治理执行记录（2026-11-09）

对已有的 127 条做了一次批量合并，全部走 `supersede`（可撤销）：

- 检出的 17 组中，**1 组（碳钢 / 铝合金）判为误判并排除**，其余 16 组按"保留表述最全
  的一条、补入其余条里未覆盖的独有句子"合并。
- 结果：**作废 22 条，有效记忆 127 → 105**，合并后复核重复组归零。
- 清理：3 组在追加时把近似同义的句子又写了一遍（只差"明确"二字之类），已改写为干净表述。
- 台账 `mem0_supersede.json` 记 22 条 `id → keep_id`，全部可一键撤销；合并明细留在
  `~/.matlens/memory_merge_log.json`（含记忆原文，**不入库**）。

顺带修掉一个会让合并看起来无效的 bug：列表接口原来只给已合并条目加 `superseded_by`
标记、却不做过滤，合并完列表条数仍是 127。现在浏览与检索都按台账过滤，`total` /
`has_more` 反映的是用户实际能看到的条数，只有显式传 `include_superseded=true` 才返回
全量（前端「已合并」视图用它）。

## 六、实体图谱：为什么是零依赖 3D

原来的实体图谱用 vis-network（2D 力导向），脚本从 unpkg CDN 动态注入，加载失败就退化成文字
列表。改造时没有换一个更大的 3D 引擎，而是自己在 canvas 2D 上算透视投影，理由有三条：

1. **量级不需要引擎。** 当前 86 实体 / 99 关系，每帧要投影的只有两百多个对象。实测单帧
   1.69 ms（60fps 的预算是 16.7 ms），引一个三维引擎反而是拿几十万字节的依赖换同样的画面。
2. **离线可用。** 旧实现在无网环境下退化成文字列表；自绘没有任何外部依赖，本地服务起不来
   时也只会显示"后端不可用"，不会因为 CDN 挂掉丢功能。
3. **神经元质感需要定制。** 节点要画成"光核 + 光晕"、连线要按深度分粗细亮度、选中时要有
   脉冲沿关系流动——这些在通用引擎里都得写自定义 shader/材质，在 canvas 里就是几次
   `drawImage` 和一条贝塞尔。

分区做法：分类 → 脑区（用户/方法/材料/性质/结论/参数/其他 七区）。七个区中心由斐波那契
球面算法生成，因此互不重叠、且**布局是决定论的**——刷新页面节点不会换个位置，方便用户记住
"哪一坨是什么"。区内节点按黄金角螺旋排布，半径带一点抖动形成"皮层厚度"。

交互：拖拽旋转（带惯性）、滚轮缩放、单击选中并高亮该实体的关系、双击进入聚焦（只亮一跳
邻居，其余压暗）、自动缓慢自转（可暂停）、重置视角。

性能四件事：

- **不可见不渲染。** 3D 只在图谱视图里跑 `requestAnimationFrame`，切回列表立刻停；图谱视图
  隐藏时容器宽高为 0，此时只缓存数据不建渲染器。
- **交互自己补帧。** 标签页不可见时浏览器会停掉 rAF，只等下一帧的话拖拽"没有反应"，
  所以拖拽/缩放/选中都同步补画一帧。
- **布局不重算。** 用实体数 + 关系数 + `updated_at` 作签名，同一版图谱切 tab 回来是瞬时的。
- **请求并行。** 记忆列表、已合并条目、重复检测三个请求互不依赖，改成 `Promise.all`
  一起发；图谱数据 8 秒内复用缓存，启动预热和切视图不再各拉一次。
